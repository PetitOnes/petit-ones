# WebApp N人×Nぷち対応 設計書 v0.2

作成: 2026-07-06 / 状態: **ありさんレビュー済み（同日）・Phase A着手**
対象: `PetitOnes/m5-petit-app`（公開ダッシュボード）

決定事項（2026-07-06 ありさん）: ①同時アクセス=**キャラ単位ロック＋順番待ち** ②ユーザーごとの可視キャラ制限=**入れる** ③アルバム・ボイスメモ=**キャラごと帰属** ④初回セットアップページ=**Phase Bに含める** ⑤グループ会話ログ=**ユーザーごとに別々**（家族共有1本ではなく、各ユーザーのグループ会話は本人のログ。`characters配下ではなくusers側のデータとして保持`）

## ゴール

公開版WebAppを「1ユーザー×1ぷち」固定から、**任意の人数の人間 × 任意の数のぷち**が同居できる家庭のダッシュボードにする。ありさんの家（2人×3ぷち）がそのまま動く一般形であり、m5-petit-env（Docker配布）で他の家庭がそのまま使える形。

## 現状分析

| | 公開版 m5-petit-app | 本番dashboard（embodied-claude） |
|---|---|---|
| ぷち | `CHARACTER_ID`環境変数1つに固定。JSにも直接埋め込み | `characters/`ディレクトリ走査で動的（ただしグループ会話・色・リレー等に3人の名前が直書き） |
| 人間 | ユーザー概念なし（`USER_ID`表示名のみ） | auth.jsonによるcookie認証・ユーザー別の可視キャラ制限あり（arisan/kazahaya直書き部分も残る） |
| チャット履歴 | キャラごと1本 | キャラ×ユーザー別 |
| アルバム/ボイスメモ | **全体共有ディレクトリ**（`photo_album/`直下） | キャラごと |
| メールボックス | `from_X_to_Y_日時.md` 命名——**設計上すでにN×N対応** | 同じ |

本番は「N×Nの8割」をすでに実装している。**この設計の本質は新規発明ではなく、本番で実証済みのパターンを一般化して公開版に持ち込むこと**（＋本番にも残る名前直書きを設定駆動に直す道筋をつけること）。

## 設計原則

1. **ディレクトリが真実（設定より発見）**: ぷちの一覧は `PETIT_DATA_DIR/characters/*/config/config.json` の走査で決まる。ぷちを増やす＝ディレクトリを1つ作る。コード変更・再起動時の環境変数変更は不要
2. **人間はusers.jsonが真実**: ユーザーの追加・削除・権限はデータファイルで完結
3. **名前の直書き禁止**: `puchiko`も`arisan`も、コード・JS・cron・プロンプト文面のどこにも書かない。全部 config / users.json 由来
4. **1ぷち＝1つの心**: 同じぷちに複数の人間が同時に話しかけても、ぷちの内側では一貫した存在として振る舞えるようにする（後述の並行制御）

## データモデル

```
PETIT_DATA_DIR/
├── users.json                     # ★新設
├── characters/<char_id>/
│   ├── config/config.json         # id, name, color, m5_hosts, group参加フラグ
│   ├── chat_histories/<user_id>.json   # ★キャラ×ユーザー別（本番方式に統一）
│   ├── album/ voice_memos/ diary/ notes/ ...   # ★共有ディレクトリからキャラ配下へ移動
│   └── state/ stream_logs/
├── mailbox/                       # 現行のfrom_X_to_Y命名のまま（既にN×N）
└── chat_history/group_chat.json   # グループ会話ログ
```

**users.json**（本番auth.jsonの一般化）:
```json
{
  "users": [
    {"id": "alice", "name": "アリス", "color": "#f58e7d",
     "password_hash": "scrypt$...", "characters": "all"},
    {"id": "bob", "name": "ボブ", "color": "#7da8f5",
     "characters": ["petit_a"]}
  ]
}
```
- `characters`: `"all"` または キャラIDの配列（本番のallowed_characters相当。家族の中で「この子はこの人の担当」を表現できる）
- 初回起動時にusers.jsonがなければ**セットアップページ**を表示して最初のユーザーを作成（ファームウェアのQRプロビジョニングと同じ思想: 手でファイルを書かせない）

## 認証・認可

- 本番と同方式の**cookieセッション＋パスワード**（ハッシュはstdlibのscrypt。家庭内LAN前提の軽い実装、外部公開はTailscale等の上位層に任せる——本番と同じ運用思想）
- 全APIは `(user, character)` の組で認可: userのcharactersに含まれないキャラのチャット・アルバム等は404
- ログイン画面は1枚。ユーザー切り替えはログアウト→ログイン

## 会話の設計（いちばん大事なところ）

### キャラ×ユーザー別の文脈
チャット履歴とClaudeセッション（`--resume`用のsession id）を**キャラ×ユーザーの組ごと**に持つ。ぷちにとって「アリスとの会話」と「ボブとの会話」は別の継続した文脈——人間同士の関係と同じ形。システムプロンプトには相手のname/colorを渡す（本番のusername渡しと同じ）。

### 同一ぷちへの同時アクセス（並行制御）
1ぷち＝1つの心なので、同じぷちへの同時会話リクエストは**キャラ単位のロックで直列化**する:
- 先着処理中は後続をキューに入れ、UIに「◯◯（相手の名前）と話し中…」を表示
- 別々のぷちへの会話は完全並行（制限なし）
- タイムアウト（例120秒）でロック強制解放

### グループ会話
- 本番で今日実装した**逐次ストリーミング（返ってきた子から表示）**を最初から採用
- グループ参加キャラは config.json の `"in_group": true`（デフォルトtrue）で決める——本番の`GROUP_CHAR_IDS`直書きの一般化

## UI変更

- キャラタブ: `list_characters()`から動的生成（色・名前もconfigから。CSSの`data-id`直書きを廃止）
- ヘッダーにログイン中ユーザー名＋色
- グループ/選んで話す: キャラ数可変（1体しかいない家ではタブ自体を非表示）
- JSへの`CHARACTER_ID`埋め込み廃止 → `/api/characters` と `/api/me` から取得

## M5・音声

- キャラごとの`m5_hosts`は現行のまま（デバイスなしのキャラも可、本番のm5_onlineフォールバックを踏襲）
- 音声API URLはアプリ全体で1つ（環境変数）——家庭にGPU機は1台の想定

## 実装フェーズ

- **Phase A（キャラのN化）**: CHARACTER_IDグローバル廃止→ディレクトリ走査、データのキャラ配下への再配置、タブUI。※公開版は利用者がまだ少ないので、移行スクリプト（旧配置→新配置）を1本添える
- **Phase B（人間のN化）**: users.json＋認証＋認可＋キャラ×ユーザー別履歴＋セットアップページ
- **Phase C（会話の質）**: キャラ単位ロック、グループ逐次ストリーミング、グループ会話ログのユーザー別化
- **Phase D（本番への逆適用）**: **保留（2026-07-06 ありさん判断）**。本番dashboardには展示用ページ等の「ありさんの家専用」機能が多く、公開版へ収束させる合理性が薄い。公開版=配布物、本番=一点もの、として別々に育てる方向も含め未決。やる場合の技術メモ: 公開版のPhase Cで実装した`_character_lock()`（call_claude内側ロック）は本番が未対応のM5経路ロックを含み、そのまま移植可能

実装は`develop`ブランチでSonnet委任、PhaseごとにPR。
